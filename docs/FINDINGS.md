# Formal Verification — Findings Log

Running log of what we learn while verifying proto-kafka against the Kafka wire protocol.
Each entry says how it was established: **verified** (read in source or reproduced) or
**unverified** (belief, pending a golden vector or harness).

Reference: Kafka 4.1.0, commit `13f70256db3c994c590e5d262a7cc50b9e973204` (`kafka_repo/`).

- About 97k lines of Rust. About 87k are generated by `protocol_codegen` into
  `src/messages.rs` and `src/messages/` (185 files, 87 API keys) from 198 JSON schemas in
  `kafka_repo/clients/src/main/resources/common/message/`. **verified**
- The hand-written core is about 10k lines: `protocol/{types,buf,mod}.rs`, `records/`,

## Divergences: crate vs. Java

### D1. `UnsignedVarInt::decode` accepts a 5th byte with the continuation bit set (crate bug)

- **Crate** (`src/protocol/types.rs:131-145`): loops `for i in 0..5`. After the 5th byte it
  exits regardless of the continuation bit, returns a value, and leaves the rest of the
  varint in the buffer. Every later field is decoded from the wrong offset.
- **Java** (`ByteUtils.readUnsignedVarint`, `clients/.../utils/ByteUtils.java:159-181`):
  throws `illegalVarintException` if the 5th byte is negative (continuation bit set).
- Bits 4–6 of the 5th byte are silently dropped by **both** implementations (`tmp << 28` in
  Java, `(b & 0x7F) << 28` on `u32` in Rust).
- Status: **verified by reading source**. `UnsignedVarLong` and the signed variants have
  not been checked yet.
- **Fixed (Phase 2, Task 3).**

### D2. Generator default rule diverged from Java (crate bug)

- Java's `FieldSpec.fieldDefault` gives `""` (string), empty (bytes/array), etc. for a
  nullable field **without** an explicit `"default"`. The default is null only for
  `"default": "null"`.
- Commit `f0b0238` made the generator default every nullable field without an explicit
  default to null (`PreparedDefault::Null`), calling this a "Kafka convention". That
  diverges from Java. Golden evidence: Java's default `RequestHeader` v1 encodes
  `client_id` as `00 00` (empty string); the generated code after f0b0238 encodes `ff ff`.
- The earlier Phase 1 note that called the committed `src/` files "stale" had it backwards:
  the committed files (except CreateTopics, hand-edited in f0b0238) matched Java; the
  generator rule was wrong.
- **Fixed (Phase 2, Task 1):** rule reverted, `src/` regenerated, `tests/golden_defaults.rs`
  pins header defaults to Java's.
- Consequence: `CreatableTopicResult::default()` now has `error_message: Some("")` and
  `configs: Some(empty)`, like Java. Code that needs null on the wire (e.g. blink's
  `src/kafka/admin.rs` CreateTopics responses, librdkafka compatibility) must set
  `.with_error_message(None)` explicitly, as Java's broker does.

### D3. Compact strings longer than 0x7fff were accepted (crate bug)
- Crate `CompactString` decoders read any compact length; Java's generated readers throw
  "string field X had invalid length" above 0x7fff (`MessageDataGenerator.java:632`). **Fixed (Phase 2, Task 4).**

### D4. Nullable struct marker misread (crate bug)
- Crate `OptionStruct` decoded `Some` only for marker `1`; Java reads the struct for any
  non-negative marker (`readByte() < 0` is null, `MessageDataGenerator.java:549`). A marker
  of `0` made the crate return `None` and misparse the struct's bytes as the next field.
  **Fixed (Phase 2, Task 4).**

### D5. Hostile lengths caused unbounded pre-allocation (crate bug, DoS)
- `Array`/`CompactArray` called `Vec::with_capacity(n)` with an attacker-controlled `n`
  (up to ~2^32) before reading; `String`/`Bytes` `Vec` decoders allocated `vec![0; n]`
  before checking the buffer; record header decoding called `IndexMap::with_capacity` on the
  declared count. A single request could make the broker abort on allocation failure. Java
  guards arrays with `length > remaining` (`MessageDataGenerator.java:656`). **Fixed (Phase 2, Task 4):**
  arrays are bounded by remaining bytes, as Java does; byte and string reads check the buffer
  before copying; header capacity is capped at the remaining bytes.

### D6. Per-record sequence ignored NO_SEQUENCE and Java's wrap rule (crate bug)
- Crate `Record::decode_new` computed `base_sequence.wrapping_add(offset_delta)`. Java
  (`DefaultRecord.java:325-327`) gives `RecordBatch.NO_SEQUENCE` when `baseSequence < 0`.
  Otherwise it uses `DefaultRecordBatch.incrementSequence` (`:557-561`), which wraps past
  `Integer.MAX_VALUE` to 0 instead of going negative. **verified** by golden vectors
  (`sequence` per record in `records.jsonl`, plus a wrap-around set: `2147483646, 2147483647, 0`).
- The encoder grouped records into a batch while `offset - sequence` stayed constant, so a list
  of Java-style records without a sequence (all `-1`) was written one record per batch.
- Found while building the D11 Java vector (2026-10-22); missed before because the spec did not
  model per-record sequences and the golden summary did not include them.
- **Fixed:** `records::record_sequence` (an `i64` formulation), proved equal to the spec's
  literal Java-`int` transcription `spec::records::record_sequence` for every
  `(i32, i32)` by Kani `proofs::records::record_sequence_conforms`. The encoder writes
  `NO_SEQUENCE` as the base for a negative first sequence, and a record joins the batch only if
  decoding gives back its sequence (and its offset is not below the base offset).

### D7. Duplicate record header keys were lost or panicked (crate bug)
- `Record::headers` was `IndexMap<StrBytes, Option<Bytes>>`. Java's `Headers` is an ordered
  list that allows repeated keys. A record with two `日` headers, from a `valid` golden vector
  written by Java's producer path, kept only the last one in release builds (data loss on
  re-encode), and panicked a `debug_assert!(headers.len() == num_headers)` in debug builds.
  **verified** by `tests/golden_crate_records.rs`.
- **Fixed (breaking):** `headers: Vec<(StrBytes, Option<Bytes>)>`. A second `debug_assert!`
  rejecting empty header keys on encode was removed too: Kafka allows empty keys.

### D8. Encoder base timestamp was the minimum, not the first record's (crate, encode only)
- Java's `MemoryRecordsBuilder` (`:471-472`) sets `baseTimestamp` from the first appended
  record, and the deltas of later records may be negative. The crate used the minimum record
  timestamp. Both decode to the same records, but the bytes and CRC differ. 6 of the 22 valid v2
  golden sets did not re-encode identically. **Fixed:** the first record's timestamp (or the
  delete horizon, D11).

### D9. Incomplete final batch (open)
- Java's `ByteBufferLogInputStream.nextBatch` returns `null` for an incomplete trailing batch,
  so the set decodes without it. Fetch responses legitimately end with one when a batch does not
  fit `max_bytes`. The crate's `RecordBatchDecoder::decode_all` / `decode_batch_info` /
  `records()` fail on the whole set. 118 Java-accepted mutated vectors hit this. It is counted
  as an allowed strictness in `tests/golden_crate_records.rs` and not fixed yet.

### D10. Record timestampDelta was a varint (crate bug)
- Java's `DefaultRecord` reads and writes `timestampDelta` as a varlong. The crate used a
  varint, so deltas beyond `i32` (about 24.8 days) failed in both directions. **Fixed** in
  `f105d6c` (upstream #159).

### D11. KIP-534 delete horizon dropped (crate bug)
- Attribute bit 6 marks a delete horizon, stored as the batch base timestamp
  (`MemoryRecordsBuilder.java:145-146`, `DefaultRecordBatch.java:250-258`). The crate ignored
  the bit, so re-encoding a compacted batch lost the horizon. **Fixed** in `2af1812`:
  `Record::delete_horizon_ms: Option<i64>`, pinned to a kafka-clients 4.1.0 batch byte for byte.
  Upstream's version (#157, a `bool`) would keep the bit but replace the horizon value.

### Debug assertions on untrusted input (crate bug, debug builds)
- Several `debug_assert!`s in `src/records/mod.rs` checked properties of untrusted input
  before an error path that already handled them: a non-empty buffer in
  `decode_optional_bytes` and `RecordIterator::new`, a count-0 batch with an empty payload, the
  header count (D7), and the encode-side version and `i32` field lengths. Hostile bytes or API
  arguments panicked debug builds instead of returning an error. Removed (2026-10-22); the
  remaining ones hold by construction.

### Other varint decoders (Phase 5 scope)

- `src/records/raw.rs:70-82` (`decode_varint`, protobuf-style u64): rejects a 10th-byte
  continuation (returns `None` once `shift >= 70`). It does not reject 10th-byte bits beyond
  bit 63 (silently dropped), so there is no `VarintOverflow` equivalent. The encoder at
  `raw.rs:92-95` is not a decoder. No other hand-rolled varint decoders exist outside
  `types.rs`, `primitives.rs` and `src/messages`.

## Java decode behaviour (ground truth for the reference spec)

All of the following were read in `generator/.../MessageDataGenerator.java`, which generates
every `*Data(Readable, short)` constructor. **verified**

- **Compact lengths:** `length = readUnsignedVarint() - 1` (Java `int` arithmetic, so it
  wraps).
- **Negative lengths:** *any* `length < 0` means null when the field is nullable in that
  version. Otherwise it throws "non-nullable field X was serialized as null". Java does
  **not** distinguish −1 from other negative values.
  The crate's `String` decoder is stricter (`-1` → None, other negatives → `NegativeLength`).
- **Strings:** `length > 0x7fff` throws. Decoding is `new String(arr, UTF_8)`
  (`Readable.java:53`), which **replaces invalid UTF-8 with U+FFFD** instead of rejecting
  it. The crate rejects invalid UTF-8 (`String::from_utf8(..)?`).
- **Arrays:** `if (arrayLength > _readable.remaining()) throw "Tried to allocate a
  collection..."`. Java caps pre-allocation at the bytes remaining. The spec's "capped
  pre-allocation" rule matches Java.
- **Tagged-field section:** `numTaggedFields`, then per entry `tag`, `size`, `switch(tag)`.
  - A known tag decodes the value directly from the stream and **ignores `_size`**.
  - A known tag that isn't valid for this version throws "Tag N is not valid for version V".
  - An unknown tag reads `size` raw bytes into `_unknownTaggedFields`.
  - **No check on tag ordering or duplicates.** A duplicated known tag means last write
    wins.
- **JSON converter is lossy for records:** `XJsonConverter.write(.., serializeRecords=true)`
  writes `records` as an **empty** `BinaryNode` (KIP-673; `JsonConverterGenerator.java:404-412`).
  Golden vectors can't rely on Java's JSON for record fields.

- **Nullable struct fields, untagged** (not arrays): a 1-byte presence marker. On read,
  `readByte() < 0` means null and anything else means present. On write, Java writes `-1`
  for null and `1` for present (`MessageDataGenerator.java:549,756,766`). **verified**
  A *tagged* nullable struct is read differently: `generateStructReader(.., tagged=true)`
  emits `if (_readable.readUnsignedVarint() <= 0) null` (`MessageDataGenerator.java:546-547`).
  The spec interpreter implements only the untagged byte form. No Kafka 4.1.0 schema has a
  tagged nullable struct (7 tagged struct fields, none nullable; scanned
  `clients/src/main/resources/common/message/*.json`), so the schema-table emitter
  (`protocol_codegen/src/generate_messages/spec_tables.rs`) refuses to emit one
  (test `rejects_tagged_nullable_struct`). Supporting it is future work. **verified**
- **Header versions** (`ApiMessageTypeGenerator.generateHeaderVersion`): the request header
  is v2 if the API version is flexible, else v1. The response header is v1 if flexible, else
  v0, **except ApiVersions (key 18) responses, which always use header v0** (KIP-511).
  Header v0 (ControlledShutdown v0) was removed in 4.0. **verified**
- **Field defaults** (`FieldSpec.fieldDefault`), used to decide whether a tagged field is
  written: **verified**
  - When `default` is absent: numbers are 0, bool is false, uuid is `ZERO_UUID`, string
    is `""`, bytes is empty, an array is empty, a struct is `new X()`, and **records is
    null**.
  - Integer defaults may be hex (`"0x7fffffff"`). JSON numbers and booleans appear both
    quoted and unquoted.
  - `"null"` is allowed only for nullable fields.
  - Default forms in the 4.1.0 schemas: `"null"`, `"-1"`, `-1`, `"0"`, `"false"`, `false`,
    `"true"`, `"-2147483648"`, `"60000"`, `"3"`, `"0x7fffffff"`, `"1"`, `1`, `""`, `16`,
    `-2`, `"9223372036854775807"`, `"2000"`.
- **Tagged field write rule:** a tagged field is written iff its value != its default (null
  compares as a distinct value) (`FieldSpec.generateNonDefaultValueCheck`). **verified**

## Consequence for the design: strictness principle

The design spec listed several strictness rules as "adopted from Java". The source shows
Java is **more lenient** than those rules in four places: negative lengths other than −1,
invalid UTF-8, tag ordering and duplicates, and known-tag size mismatch. The resolved rule
is:

> **On well-formed input, the reference spec equals Java. On malformed input, the spec may
> be stricter than Java (reject), never more lenient.** Every case where it is stricter is
> listed here and in `verification/DIVERGENCES.md`.

Deliberately stricter cases so far:

| # | Input | Java | Spec / crate |
|---|---|---|---|
| S1 | Length prefix < −1 on a nullable field | null | reject |
| S2 | Invalid UTF-8 in a string | lossy U+FFFD | reject |
| S3 | Tagged fields duplicated or out of order | accepted (last wins) | reject |
| S4 | Known tagged field whose value length ≠ declared `size` | accepted (size ignored) | reject |
| S5 | 5th varint byte with bits 4–6 set (or 10th varlong byte > 0x01) | bits dropped | reject |
| ~~S6~~ | Record batch magic byte other than 0/1/2 | **retracted**: Java's wire path rejects it (see Phase 1 results) | reject (not Strict) |
| S7 | Tagged-field count >= 2^31 | `int _numTaggedFields` is negative, loop runs zero times: accepted as empty | reject |

S4 also covers a known tag whose value runs past its declared `size` window, including an
array whose length exceeds the window but not the whole buffer: Java checks
`arrayLength > _readable.remaining()` against the whole buffer
(`MessageDataGenerator.java:653-657`), so the strict spec reports S4 there, not
`ArrayTooLong`. **verified**

S7 source: `MessageDataGenerator.java:478-479` emits `int _numTaggedFields =
_readable.readUnsignedVarint(); for (int _i = 0; _i < _numTaggedFields; _i++)`, and
`ByteUtils.readUnsignedVarint` (`ByteUtils.java:159-181`) returns the raw 32 bits as an
`int`. Test: `spec/tests/interp_decode.rs::tag_count_at_or_above_2_pow_31`. **verified**

### Java-lenient decode mode

`interp::decode_with(.., Mode::JavaLenient)` and `records::decode_with(.., Mode::JavaLenient)`
reproduce Java's acceptance on exactly the S1-S5 and S7 inputs: any negative length is null
on a nullable field (`Utils.readBytes` / `Utils.sizeDelimited` for records), the final varint
byte's extra bits are dropped (`ByteUtils.readUnsignedVarint` `tmp << 28`,
`readUnsignedVarlong` `b << i`, `ByteUtils.java:159-181, 299-311`), invalid UTF-8 is kept as
raw bytes (Java: lossy `new String(.., UTF_8)`, `Readable.java:51-54`), tagged fields are read
in any order with last-write-wins for known tags and the known tag's value read from the main
stream with `_size` ignored (`MessageDataGenerator.java:478-528`), and a tag count >= 2^31 is
an empty section. `decode` stays strict and is the reference semantics; the lenient mode
exists so the golden tests can compare every Java-accepted vector with Java's value. Unit
tests: `java_lenient_*` in `spec/tests/{wire,interp_decode,records}.rs`. **verified**

## Phase 1 results (golden conformance)

Golden vectors from kafka-clients 4.1.0 (`verification/golden/vectors/`, `wc -l`):
`messages.jsonl` 11,760 (588 default, 1,764 random, 2,869 mutated that Java accepts,
6,539 mutated that Java rejects), `headers.jsonl` 292, `records.jsonl` 494 (38 valid;
`mutated`: 97 Java-accepted, 131 rejected; `mutated_crc_fixed`: 145 Java-accepted, 83
rejected). Total 12,546.

What the golden tests assert (`spec/tests/golden_{messages,records}.rs`):

- Java accepts: the `Mode::JavaLenient` decode equals Java's value (message strings and
  record header keys compared after lossy UTF-8 decoding, as Java does) and, for messages,
  Java's consumed length. The strict decode either equals the lenient decode or is
  `Err(SpecError::Strict(_))`, and the latter only on mutated vectors. Default, random and
  valid message vectors also re-encode byte-for-byte.
- Java rejects: both the strict and the lenient decode reject, except record sets the spec
  accepts only through an opaque compressed payload (counted separately; see "Compressed
  payloads" below).
- The strict-rejection histograms and the opaque-compressed count are asserted exactly.

Strict rejections (spec rejects, Java accepts) in the final run, all on mutated vectors:

- messages: `{"S1NegativeLength": 45, "S2InvalidUtf8": 439, "S3TagOrder": 1, "S4TagSize": 6}`
- records: `{"S1NegativeLength": 8, "S2InvalidUtf8": 2}` (all from `mutated_crc_fixed`)
- records accepted by the spec's opaque compressed path where Java rejects: 1 (a v2 batch
  re-stamped with codec 4/zstd and a garbage payload: "Failed to decompress record stream")

No S5 or S7 case occurs in the vectors. They are covered by unit tests in
`spec/tests/wire.rs` and `spec/tests/interp_decode.rs`.

The `mutated_crc_fixed` vectors reach Java's record-level checks (Java errors among the 83
rejections include "Found invalid record structure", "Invalid negative header key size",
"Found invalid number of record headers", "Invalid record size: expected to read",
"Incorrect declared batch size, premature EOF reached", "Unknown compression type id: 7")
and found no new spec bug: the spec rejects every one of them, and the lenient decode matches
Java on all 145 accepted ones.

### Compressed payloads

The spec does not decompress or validate compressed payloads (v2 batches with codec 1-4 and
records; legacy wrappers with codec 1-3). This is a design non-goal, and it makes the spec
**more lenient than Java** on such input: Java decompresses and parses the inner records
(`DefaultRecordBatch.compressedIterator`, `AbstractLegacyRecordBatch.DeepRecordsIterator`)
and rejects corrupt contents. It is the one listed exception to the strictness principle.

Spec bugs found and fixed:

- **G1. Invalid magic in a truncated final record batch.** Java's wire path
  (`MemoryRecords.batches()` -> `ByteBufferLogInputStream.nextBatchSize`,
  `clients/.../common/record/ByteBufferLogInputStream.java:66-86`) reads the size, throws
  if it is below `RECORD_OVERHEAD_V0`, returns null if fewer than `HEADER_SIZE_UP_TO_MAGIC`
  (17) bytes remain, and then throws `CorruptRecordException("Invalid magic found in
  record: N")` for magic < 0 or > 2 (line 84). All of that happens **before** `nextBatch`
  checks that the whole batch is present. The spec returned such a batch as a
  `truncated_tail`. 5 golden vectors (magic 44, 4, 17, -1, 75). Fix: `records::decode`
  checks the magic as soon as byte 16 is present. Regression test:
  `spec/tests/records.rs::invalid_magic_in_truncated_tail_is_rejected_like_java`.
  **verified** (golden vectors plus source).
- **S6 retracted.** The same check means Java rejects an unknown magic on complete
  batches too, so S6 ("treated as v2, accepted") was wrong for bytes read off the wire.
  Only the broker's on-disk reader (`FileLogInputStream.java:83-89`) routes magic >= 2 to
  `DefaultFileChannelRecordBatch` without that check. The spec now rejects unknown magic
  with `SpecError::Records`, and `Strict::S6UnknownMagic` was removed. Test:
  `spec/tests/records.rs::unknown_magic_is_rejected_like_java`. **verified**

- **G2. v2 batch: empty batch vs. codec (final review I3).** Java
  `DefaultRecordBatch.iterator()` (`clients/.../common/record/DefaultRecordBatch.java:320-325`)
  returns `Collections.emptyIterator()` when `count() == 0` **before** anything else, so an
  empty batch with trailing bytes after the header, or with any codec id, is accepted with
  no records. Only then does `isCompressed()` -> `compressionType()` ->
  `CompressionType.forId` (`CompressionType.java:144-158`) throw
  `IllegalArgumentException` for codec ids 5-7, and `RecordIterator`'s constructor
  (`DefaultRecordBatch.java:583-586`) rejects a negative count. The spec rejected
  count-0-with-trailing-bytes (non-Strict, a false rejection) and accepted codecs 5-7 as
  `Payload::Compressed` (more lenient than Java). Fix: `records::decode_v2` follows Java's
  order. Tests: `spec/tests/records.rs::empty_batch_ignores_trailing_bytes_and_codec`,
  `unknown_codec_with_records_is_rejected_like_java`. **verified** (source).
- **G3. Legacy message codec checks.** Java `AbstractLegacyRecordBatch.iterator()`
  (`AbstractLegacyRecordBatch.java:234-236`) calls `isCompressed()`, i.e.
  `LegacyRecord.compressionType()` -> `CompressionType.forId(attributes & 0x07)`
  (`LegacyRecord.java:242-243`), which throws for 5-7. `DeepRecordsIterator`
  (`AbstractLegacyRecordBatch.java:322-334`) then rejects a ZSTD (4) wrapper and a wrapper
  whose value is null. The spec ignored the legacy codec bits and accepted all of these.
  Fix: `records::decode_legacy` rejects codec 4-7 and a null-valued compressed wrapper;
  codecs 1-3 stay opaque (see "Compressed payloads"). Test:
  `spec/tests/records.rs::legacy_codec_checks_follow_java`. **verified** (source).

No message-interpreter (`interp`/`wire`) bug was found by the vectors. Precisely: every
default and random message vector decodes strictly to Java's value and consumed length and
re-encodes byte-for-byte; every Java-accepted mutated message vector (2,869) decodes in
`JavaLenient` mode to Java's value and consumed length, and in strict mode either to the same
value (2,378) or to a listed `Strict` rejection (491). Header versions match Java for all 292
request API versions. The final review (I1) found that before the lenient mode existed, the
491 strict-rejected vectors were not compared with Java at all; they are now.

Final status: `golden_headers`, `golden_messages` (including
`golden_covers_every_message_version`) and `golden_records` pass.

Task 6 (framing and `unsafe` sites). Same command and environment. 18 Task 6 harnesses verified, 7 decode harnesses blocked, no counterexamples, no crate-vs-spec divergences found. Task 5's 17 harnesses re-verified unchanged.

Bounds were split per concrete length (`_lenN`, `_pP_kK`) instead of the brief's `len: usize = kani::any(); &buf[..len]`. A symbolic slice length makes CBMC model `memcpy`/UTF-8 validation over symbolic-size arrays, so `strbytes_from_utf8_is_exactly_utf8` and `string_encode_ascii` timed out or ran out of memory. Split per length, each one finishes in under 20s. The union of the split harnesses covers the same input set as the original bound.

**`StrBytes` constructor audit.** The tuple field of `StrBytes` is private to `protocol::str_bytes`, and the only `Self(..)` sites are `new` (empty `Bytes`), `from_static_str` (from `&'static str`), `from_string` (from `String`) and `from_utf8` (validates with `std::str::from_utf8`). `From<&'static str>`, `From<String>` and `TryFrom<Bytes>` delegate to these. The derived `Default` (empty `Bytes`) and `Clone` (copy of a valid value) also preserve validity. No serde or other impls construct one, and `GroupId`/`TopicName`/`TransactionalId` wrap an existing `StrBytes`. Only `from_utf8` takes unchecked bytes, and the `strbytes_*` harnesses prove it accepts exactly valid UTF-8 and `as_str` returns the same bytes. The `from_utf8_unchecked` in `as_str` is sound.

**`SegmentedBuf::advance_mut`.** The forwarded `BytesMut` contract is model-checked (`bytesmut_*`). The `SegmentedBuf` wrapper is argued by hand, because Kani cannot handle it. `chunk_mut` calls `current_inline()`, which makes the last segment `Inline`, and returns that segment's spare capacity. Nothing can change the segment list between `chunk_mut` and the caller's `advance_mut` (both take `&mut self`, and the caller only writes into the returned slice). So `advance_mut`'s own `current_inline()` finds the same `Inline` segment and forwards `cnt`, then adds `cnt` to `total_len`. If a caller breaks the contract and calls `advance_mut(cnt > 0)` without `chunk_mut`, it gets either that same segment or a fresh empty `BytesMut`. `BytesMut::advance_mut` panics when `cnt` exceeds spare capacity (bytes 1.12, `panic_advance`), so the result is a panic, not UB. Why Kani cannot handle the wrapper: a `BytesMut` held inside the segment `Vec` has its pointer fields (including the int-tagged `data`) stored in heap memory, which CBMC models as bytes. Even the fully concrete `SegmentedBuf::new(); sb.chunk_mut()` (push + `reserve(8192)`) does not finish propositional reduction in 250s. Every variant tried also timed out: P = 0/2, K = 0/3, unwind 2/3/6, CaDiCaL, `--arrays-uf-always`, `mem::forget`, no read-back. The Z3 backend crashes CBMC (`map::at: key not found`). The same operations on a stack `BytesMut` take 0.8s. Before this work, both unsafe-site harnesses had been reported as FAILED. That was CBMC out-of-memory ("CBMC appears to have run out of memory"), not a failed check, made worse by four orphaned `cbmc` processes from a killed earlier run.

**Task 6 blocker: decode harnesses vs `interp::decode`.** None of the seven decode harnesses terminates, and the input bound is not the cause: a fully concrete 3-byte input does not finish symbolic execution in 240s at unwind(10), and symbolic N = 3 at unwind(4) does not finish in 300s either. `interp::decode` builds and drops a recursive `Value` tree (`Array(Vec<Value>)`, `Struct(Box<StructValue>)`, `unknown_tags: Vec<(u32, Vec<u8>)>`) through heap memory: `read_struct`'s `vec![None; n]` slots, the zip `IntoIter`, and drops on `?` error paths. CBMC loses the enum discriminant through the heap and unrolls `drop_glue::<Value>` to the unwind depth at about 130-150 sites ("Not unwinding recursion drop_glue::<Value>"). The harness-side `mem::forget` of the spec result does not help, because the drops are inside the interpreter. The encode direction is unaffected (`compact_bytes_encode`, `string_encode_ascii_*` pass), because there the harness builds the `StructValue` concretely. The harnesses stay in `src/proofs/framing.rs` as unregistered functions marked BLOCKED. Possible ways to unblock, all outside Task 6 scope: (a) a Value-free spec entry point for one primitive/array field (for example a `pub` `read_prim`-style function over `wire::Reader`), against which the crate decoders can be checked while `interp::decode` keeps using it; (b) Kani stubbing (`-Z stubbing`) of the interpreter's struct plumbing; (c) exhaustive bounded unit tests (crate vs `interp::decode` on every input up to 3 bytes, plus structured length-prefix enumeration) in place of Kani.
